# Design

## Context

SvelteKit 3 (adapter-node, Node 24) with shadcn-svelte, `#lib` subpath imports, Vitest (Node + browser) and Playwright e2e against `node --import ./src/mocks/preload.ts build`. An MSW mock bridge (`src/mocks/bridge/`) answers at `192.0.2.10` in tests. `/healthz` exists. No server code talks to a bridge yet, and there is no `hooks.server.ts`.

Facts the design relies on:
- Pairing: `POST https://<bridge>/api` with `{"devicetype":"<app>#<device>","generateclientkey":true}`. Before the link button is pressed it returns `[{"error":{"type":101,...}}]`; after, `[{"success":{"username":"<app key>","clientkey":"..."}}]`. CLIP v2 requests send the key in the `hue-application-key` header.
- `GET https://<bridge>/api/0/config` answers without a key and includes `name`, `bridgeid`, `modelid`, `swversion`. Used to check that an address is a Hue bridge.
- Cloud discovery: `GET https://discovery.meethue.com/` returns `[{"id","internalipaddress","port"}]` and is rate-limited.
- Bridge certificates are not browser or Node trusted (Signify CA on newer bridges, self-signed on older ones). openhue-cli disables verification; this design pins instead (user decision).
- Node 24.22 bundles undici 7.30.1. An `undici@7` `Agent` can be passed to the global `fetch` as `dispatcher`.

Library evidence (2026-10-29):

| Package | Version | Last publish | Use |
|---|---|---|---|
| openhue-api spec | release 1.2 (`openhue.yaml` asset) | 2026-04-15 | CLIP v2 OpenAPI spec |
| `openapi-typescript` | 7.13.0 | 2026-06-15 | Generate types from the spec |
| `openapi-fetch` | 0.17.0 | 2026-06-15 | Typed fetch client, accepts a custom `fetch` |
| `undici` | 7.30.x (match Node) | 2026-10-19 (8.12.3 latest) | `Agent` with a pinning connector |
| `zod` | 4.6.7 | 2026-10-12 | Validate `config.json` and bridge responses |
| `openapi-msw` | 2.1.1 (peer `msw ^2.10.5 \|\| ^3`) | 2026-10-27 | Typed mock handlers |

Alternatives considered: `node-hue-api`, `hue-sync`, `open-hue` (all stale since 2023-2024, see project-setup exploration); `valibot` instead of zod (smaller, but zod is more widely known and also maintained; size does not matter on the server); `undici@8` (major mismatch with Node's bundled undici risks `dispatcher` incompatibility).

## Goals / Non-Goals

**Goals:**
- A user pairs from the browser in under a minute, with clear errors for each failure in the specs.
- The app key never leaves the server.
- Pinning is exercised by an e2e test over real TLS, not only unit tests.

**Non-Goals:**
- Multiple bridges, mDNS, dashboard auth, removing the app key from the bridge.
- Rooms, lights, or scenes (room-control, scenes).

## Decisions

### Module layout
```
src/lib/server/hue/
  openhue.yaml        vendored spec, release 1.2
  schema.d.ts         generated by `pnpm gen:hue` (openapi-typescript), committed
  tls.ts              pinning Agent factory + fingerprint capture
  client.ts           createHueClient(config) -> openapi-fetch client with pinned dispatcher, 5 s timeout
  bridge.ts           getPublicConfig(address), requestAppKey(address), checkBridge(config)
  discovery.ts        discoverBridges() via discovery.meethue.com, 10 s timeout
  address.ts          parse/validate "host[:port]"
src/lib/server/config/
  store.ts            read/write config.json (zod schema, atomic write, mode 0600)
  index.ts            getBridgeConfig(): env vars > config.json > null
src/hooks.server.ts   setup redirect
src/routes/setup/     +page.server.ts (actions: discover, check, pair), +page.svelte
src/routes/+page.server.ts, +page.svelte   connected view, forget action
```
`schema.d.ts` is committed so builds and CI do not need network access. `pnpm gen:hue` regenerates it from the vendored spec.

### TLS pinning
`tls.ts` builds an `undici` `Agent` whose `connect` option wraps `buildConnector({ rejectUnauthorized: false })`. After the TLS handshake it reads `socket.getPeerCertificate().fingerprint256`, normalizes it (uppercase hex, no colons), and:
- **capture mode** (setup): records the fingerprint and continues.
- **pinned mode**: compares with the stored fingerprint. On mismatch it destroys the socket with a `CertificateMismatchError` before any HTTP bytes are written, so the app key is never sent.

All bridge requests use `globalThis.fetch(url, { dispatcher, signal: AbortSignal.timeout(5000) })`.

Env mode without `HUE_BRIDGE_CERT_SHA256` uses capture mode once, then switches the process-wide agent to pinned mode and logs the fingerprint.

Alternatives: disabling verification (rejected by the user); shipping Signify's CA (does not cover older self-signed bridges and needs a hostname check against the bridge ID).

### Config store
`config.json` schema (zod): `{ version: 1, bridge: { address, id, name, appKey, clientKey, certSha256 }, pairedAt }`. Write path: `writeFile(tmp, data, { mode: 0o600 })` then `rename(tmp, config.json)` in the same directory. `HUE_DATA_DIR` overrides `/data` (used by tests). Reads are cached in memory and invalidated on write/delete.

### Setup flow
- `hooks.server.ts`: if `getBridgeConfig()` is null and the path is not `/setup` or `/healthz`, redirect 303 to `/setup`. If configured and the path is `/setup`, redirect to `/`.
- `/setup` uses SvelteKit form actions with `use:enhance`:
  - `discover`: calls discovery, returns the list or an error code.
  - `check`: validates the address, calls `/api/0/config` in capture mode, verifies the response shape (`bridgeid` and `modelid` present), and stores a pending pairing `{ address, id, name, certSha256 }` in server memory under a random token set as an `httpOnly` cookie (expires after 5 minutes).
  - `pair`: one `POST /api` attempt with the pending pairing's pinned agent. Returns `waiting` on error 101, or saves the config and redirects to `/` on success.
- The page drives the 60 s loop: after `check` succeeds it calls `pair` every 2 s and shows a countdown. Stopping on timeout is client-side; the server also rejects `pair` after the pending pairing expires.
- `devicetype` is `huedash#<hostname>`, truncated to the bridge limits (20 / 19 characters).

UI uses shadcn-svelte `Card`, `Field`, `Input`, `Button`, `Alert`, `Spinner`, `Empty`, `AlertDialog` (added with the CLI as needed).

### Home page
`+page.server.ts` `load` returns `{ name, source: 'env' | 'file', status }`, where `status` is a streamed promise from `checkBridge()` (`GET /clip/v2/resource/bridge`) that resolves to `ok`, `unreachable`, `unauthorized`, or `certificate-mismatch`. The page renders the name at once and the status when it arrives. `forget` is a form action guarded by `AlertDialog`; it is not rendered in env mode.

### Mock bridge
- Handlers use origin wildcards (`*/api/0/config`, `*/api`, `*/clip/v2/...`) so the same handlers work for `192.0.2.10` in unit tests and for the e2e HTTPS server.
- CLIP v2 handlers use `openapi-msw` with the generated `paths` types. The `/api` and `/api/0/config` handlers are plain MSW (v1, not in the typed paths beyond `POST /api`).
- Pairing state: the `/api` handler returns error 101 until `pressLinkButton()` is called; the e2e preload calls it after the first attempt so the flow completes on the second poll.
- Discovery handler for `https://discovery.meethue.com/` returns the e2e bridge address.

### E2E over real TLS
The e2e preload starts:
1. An `https.createServer` on `127.0.0.1:8443` with a committed test certificate (`src/mocks/bridge/tls/`), answering every request with MSW 3's `getResponse(handlers, request)`.
2. MSW `setupServer` with only the discovery handler, and `onUnhandledFrame` that bypasses `127.0.0.1:8443` and errors on everything else.

`playwright.config.ts` sets `HUE_DATA_DIR` to a fresh temp dir and no longer sets `HUE_BRIDGE_IP`. The setup e2e test enters `127.0.0.1:8443`, so pinning, capture, and pairing run over real TLS. A second test certificate lets a unit test prove that a changed certificate is rejected.

Test certificates are generated once with `openssl` and committed; they protect nothing.

## Risks / Trade-offs

- [Cloud discovery is rate-limited] → Only on user click; a 429 maps to "discovery failed, enter the IP" with a short hint. No caching for now.
- [Bridge replaced or certificate renewed by firmware] → Shows the certificate-changed state with a forget-and-re-pair path. Acceptable for a LAN app; documented in README.
- [`rejectUnauthorized: false` during capture] → Only for `/api/0/config` during setup, before any key exists. The fingerprint shown in the UI next to the bridge ID lets careful users compare.
- [In-memory pending pairing] → Lost on restart; the user starts setup again. Single instance only, which matches the self-hosted model.
- [undici major must match Node] → Pinned to `^7`; a Node upgrade that bundles undici 8 needs a matching bump. Covered by the TLS unit tests.
- [`schema.d.ts` drift from bridge firmware] → Regenerate when bumping the vendored spec; types are only compile-time.

## Changes found during implementation

- Runtime libraries (`openapi-fetch`, `undici`, `zod`) are devDependencies, like everything else. SvelteKit externalizes `dependencies` from the server bundle, and the runtime image has no `node_modules`. Task 6.3 re-checks that `node build` runs without `node_modules`.
- `openapi-typescript` 7.13 declares a peer of TypeScript 5; the project uses TypeScript 6. Generation is checked in task 1.2.
